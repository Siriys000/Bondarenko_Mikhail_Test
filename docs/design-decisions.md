# Design decisions

## Разделение слоёв и ООП

Домен и прикладные сервисы не зависят от FastAPI, Celery и SQLAlchemy.
Классы имеют конкретные обязанности: HTTP-клиент, репозиторий, сборщик и сервис чтения.
Зависимости передаются через конструкторы, поэтому тесты подменяют инфраструктуру,
не вмешиваясь в бизнес-логику. Protocol позволяет сохранить типизацию без дополнительных
базовых классов. Отдельный универсальный Unit of Work не нужен: каждая цена записывается
одной независимой транзакцией.

## SQLAlchemy 2, PostgreSQL и миграции

SQLAlchemy предоставляет параметризованные запросы и явное управление сессиями.
PostgreSQL обеспечивает ограничения и атомарную защиту от дублей, в том числе при конкуренции.
Alembic создаёт схему до старта сервисов; приложение не вызывает `create_all()`.
Миграции используют синхронный psycopg, API и сборщик — asyncpg.

## Decimal и UNIX timestamp

JSON биржи разбирается с `parse_float=Decimal`, поэтому цена не проходит через двоичный float.
Хранение в `NUMERIC(28, 12)` даёт 16 разрядов целой части и 12 дробной.
Клиент отклоняет недопустимые и слишком точные значения вместо скрытого округления.
В HTTP-ответе Decimal сериализуется строкой, чтобы потребитель мог сохранить точность.

Время хранится в UNIX seconds по условию задания. Это время успешного наблюдения на нашей стороне,
а не время торговой сделки или метка микросекунд из служебного поля Deribit.
Фильтр использует читабельные календарные дни UTC. Последний день включён целиком:
SQL использует полуоткрытый диапазон `[начало первого дня, начало следующего дня)`.

## Контракт Deribit

Клиент вызывает публичный GET `/api/v2/public/get_index_price` с `index_name=btc_usd`
или `eth_usd` и использует `result.index_price`. Ключи API не нужны.
`estimated_delivery_price` и служебные поля не используются.
Контракт: [официальная спецификация метода](https://docs.deribit.com/api-reference/market-data/public-get_index_price).

Проверяется как HTTP-статус, так и JSON-RPC `error` при HTTP 200.
Повторяются сетевые ошибки, таймауты, HTTP 408/429/5xx и временные RPC-коды
10028, 10040, 10066, 11051, 11094. Остальные RPC-ошибки и некорректный контракт
логируются без повторов текущего запуска.
Основание классификации: [таблица ошибок Deribit](https://docs.deribit.com/articles/errors).

## Celery Beat и Redis

Beat отправляет задачу на каждой минутной границе UTC, Worker выполняет сбор.
Redis используется только как брокер. Result backend отсутствует: полезные результаты
хранятся в PostgreSQL. Нужен один экземпляр Beat; дополнительные воркеры допустимы.
Задачи подтверждаются после выполнения, prefetch равен 1.
Устаревшее сообщение первоначального запуска имеет TTL 55 секунд.

Маленький `MinuteSlotScheduler` добавляет `collection_slot` в сообщение до публикации.
Поэтому задержка, повтор и повторная доставка после потери воркера не меняют идентификатор запуска.
При ручном запуске без слота используется текущая минута воркера.

Ограничения Redis как брокера приемлемы для минутных снимков: потерянные снимки не восстанавливаются
из более поздней текущей цены. Длительный простой оставляет честный пробел в истории.

## Повторы и частичный успех

Повторами управляет только Celery: по умолчанию три повтора после первой попытки,
с задержками 2, 4 и 8 секунд. Внутреннего второго цикла retry в HTTP-клиенте нет.
Таймаут HTTP — 10 секунд, значения настраиваются через окружение.
Временная недоступность БД также допускает повтор задачи.

Успешная цена одной валюты коммитится независимо от другой. Перед повторным запросом
проверяется сохранённый слот, поэтому успешно обработанная валюта не опрашивается повторно.
Проверка `exists()` сокращает запросы; уникальность в БД обеспечивает корректность при гонке.
Второй воркер может успеть обратиться к бирже, но повторную запись не создаст.
При исчерпании повторов ошибка остаётся в логах Worker.

## REST API и пагинация

API предоставляет ресурсы чтения `/prices`, `/prices/latest`, `/prices/history`.
Все операции — GET, в каждой требуется query-параметр `ticker`.
Неизвестный тикер — 422, пустая история — 200 с `[]`, отсутствие последней цены — 404,
временная недоступность БД — 503. Тикеры нормализуются к нижнему регистру.

Без `limit` возвращаются все записи, как требуется в задании. Для больших историй
можно явно передать `limit` (1–10000) и `offset`. Сортировка по времени возрастает.
Offset выбран из-за простоты интерфейса; большие offset и полный ответ менее эффективны,
чем cursor pagination. Для этого масштаба отдельный cursor-контракт не вводится.

## Контейнеры и конфигурация

API, Worker и Beat запускаются отдельно и могут независимо перезапускаться.
PostgreSQL сохраняет данные в named volume. Redis не требует хранения результатов задач.
Одноразовая миграция отделена от старта каждого воркера. Это добавляет сервис `migrate`,
зато исключает одновременную миграцию несколькими процессами.
Контейнер приложения работает от непривилегированного пользователя.

`.env.example` содержит только настройки локальной разработки; `.env` исключён из Git
и Docker build context. Версии зависимостей зафиксированы в `uv.lock`.

## Тесты и QA

Unit-тесты проверяют прикладную логику, API и управление повторами.
Клиент проверяется на локальном HTTP-сервере с ответами по официальному контракту.
Тесты не вызывают реальную биржу и не требуют её доступности.
Интеграционные тесты используют настоящий PostgreSQL: точность NUMERIC, выборку,
ограничения и конкурентный `ON CONFLICT`. SQLite не заменяет PostgreSQL в этих проверках.

Ruff проверяет стиль и распространённые ошибки, mypy работает в strict-режиме.
Нетипизированная граница Celery изолирована в модуле Worker; отключение проверок
не распространяется на домен, API и репозиторий.
GitHub Actions запускает QA, миграции, проверку расхождения схемы и сборку Docker.
